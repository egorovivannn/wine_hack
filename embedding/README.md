## Данные и идентичность вина

Метаданные: `data/WineSensed/metadata/images_reviews_attributes.csv`.
Класс — исходный `vintage_id`: конкретное вино конкретного урожая. Разные годы остаются разными классами.
Целочисленный `label` — воспроизводимое отображение этих ID, а `wine_id` сохраняет исходный ключ.
Назначать классы по имени файла или `winery_id` нельзя: файл обозначает снимок, winery — производителя.

Итог: `data/winesensed_embedding/dataset.csv`: **122651 кроп, 75936 классов**.
Обработаны все 996776 однозначно размеченных исходников; 32 файла исключены до детекции из-за противоречивых ID.
Полная проверка декодирования кропов завершена без ошибок; пересечений классов и точных дубликатов нет.

| Split | Классы | Изображения |
|---|---:|---:|
| train | 68342 | 91638 |
| val | 3797 | 14930 |
| test | 3797 | 16083 |

Первые колонки:

| Колонка | Значение |
|---|---|
| `image_path` | Полный абсолютный путь к JPEG-кропу |
| `label` | Целочисленный идентификатор класса |
| `split` | `train`, `val` или `test` |
| `wine_id` | `winesensed:<vintage_id>` |
| `source_path` | Путь к исходному изображению |
| `bbox` | `[x1,y1,x2,y2]` в пикселях, правый/нижний край исключены |
| `confidence` | Уверенность детектора |
| `source_sha256`, `crop_sha256` | Хеш исходных байтов и декодированных пикселей кропа |

В датасете нет bbox. Используется локальный обученный детектор
`detection/runs/grain_yolo26s/weights/best.pt`, класс `wine_bottle`.
Его сохранённый тестовый mAP50–95 — 0.8588 **на собственном детекторном тесте**, не на WineSensed.
Изображения декодируются OpenCV с той же ориентацией, что и при детекции.
Кропы сохраняются отдельно: `data/winesensed_embedding/crops/<prefix>/<id>.jpg`, JPEG quality 95.

Правила очистки:

- Исключаются файлы, которым метаданные назначают несколько разных `vintage_id`.
- Детекции считаются от confidence 0.25. Сохраняется только кадр с ровно одной детекцией.
- В учебный CSV попадают кропы с confidence ≥ 0.50 и обеими сторонами ≥ 24 px.
- Изображения без бутылки, с несколькими детекциями или ошибкой декодирования записываются в отчёт.
- Точные дубликаты исходного файла или пикселей кропа удаляются **до** разделения.
- Если точный дубликат подписан разными ID, неоднозначные экземпляры исключаются.

Ошибки исходной разметки и детектора полностью автоматически не устраняются. В частности, одна
найденная бутылка не доказывает, что других бутылок на фотографии нет. Это псевдоразмеченный бейзлайн;
разбор оставшихся ошибок — следующий этап. Близкие, но не точные дубликаты пока не объединяются.
Кропы, исключённые при финальной фильтрации, могут оставаться на диске; для обучения источником истины служит CSV.

`report.json` содержит итоговые числа и причины исключения, `labels.csv` — соответствия ID,
`rejected.csv` и `metadata_rejected.csv` — исключённые записи.
`detections.sqlite` — журнал обработки, `sources.csv` — индекс оригиналов.
Повторный запуск продолжает обработку по журналу. При изменении весов/настроек детекции нужен другой `--output`.

```bash
cd /mnt/SSD/workspace/wine
python -m embedding.prepare
```

## Разбиение и метрики

**90% / 5% / 5% по классам**, а не по изображениям. Пересечений `vintage_id` между частями нет.
Доли округляются до целого числа классов. Seed 42.
Для val/test случайно выбираются классы минимум с двумя различными пригодными снимками;
классы с единственной фотографией остаются в train. В отчёте отдельно приведены доли классов и изображений.

Валидация: все изображения val сравниваются со всеми изображениями val.
Тест: все изображения test сравниваются со всеми изображениями test.
**Собственный индекс запроса маскируется значением −∞ до top-k.**
В тесте нет изображений или классов из train/val. Галерея из train не используется.

- **Recall@1**: доля запросов, у которых ближайшая *другая* фотография принадлежит тому же классу.
- **Recall@5**: доля запросов, у которых хотя бы одна из пяти ближайших *других* фотографий принадлежит тому же классу.
- Основная метрика усредняется по изображениям. Дополнительно считается macro Recall: сначала по запросам каждого класса, затем по классам.
- Top-5 — пять изображений, не обязательно пять разных классов; это стандартная image retrieval оценка.
- Все запросы имеют хотя бы один положительный пример благодаря правилу ≥2 снимков для val/test.
- Поиск точный, по cosine similarity нормализованных эмбеддингов; матрица обрабатывается блоками без выделения полной N×N матрицы.

По умолчанию после каждой эпохи считается **полная all-vs-all валидация**.
Опция `--val-query-limit 5000` оставляет фиксированные 5000 запросов для ускоренного мониторинга,
но поиск всё равно идёт по всей val-части. Это отдельный режим, а не полная оценка.
Команда `embedding.evaluate` всегда оценивает весь выбранный split.
Лучшая модель выбирается по val Recall@1. Test следует запускать после выбора модели, не подбирать по нему параметры.

## Модель и обучение

**DINOv2 ViT-L/14**, 304.9 млн параметров с проекцией, предобученные веса уже находятся
в `detection/models/dinov2-large`. CLS → LayerNorm → Linear(1024,512) → L2 normalization.
Это сильный доступный визуальный бейзлайн; превосходство над всеми альтернативами на этих данных не проверялось.
Основа выбора — [официальный DINOv2](https://github.com/facebookresearch/dinov2) и его
[реализация Transformers](https://huggingface.co/docs/transformers/en/model_doc/dinov2).
Более новый [DINOv3](https://github.com/facebookresearch/dinov3) можно сравнить позже: его веса требуют отдельного получения доступа.

Дообучаются все 24 блока и входные параметры backbone. Можно уменьшить число обучаемых блоков через `--train-blocks`.
Разрешение **518×224**, letterbox с сохранением пропорций: бутылка не растягивается и не обрезается случайным crop.
Минимальная аугментация — лёгкий ColorJitter. Отражений текста и случайного удаления частей этикетки нет.

Loss — supervised contrastive (SupCon), temperature 0.07.
Один физический батч: **32 вина × 2 снимка = 64**. Классы выбираются равновероятно, снимки внутри класса — случайно.
Для одиночных train-классов используются два слегка изменённых вида одного снимка; это не независимые фотографии.
Gradient accumulation 2 даёт размер шага оптимизатора 128, **но не увеличивает число негативов в loss**:
в одном contrastive батче их 62 на запрос.

AdamW, backbone LR 1e-5, head LR 1e-4, warmup + cosine decay, clipping градиентов.
BF16 по умолчанию, FP16 + GradScaler также поддержан (`--precision fp16`). BF16 поддерживается RTX 3090 Ti
и устраняет необходимость масштабирования градиентов. Используются SDPA attention,
gradient checkpointing, pinned memory, persistent workers, fused AdamW и `zero_grad(set_to_none=True)`.
Точный поиск метрик выполняется с FP32 similarity без TF32.

Технический запуск на RTX 3090 Ti: batch 64, все 24 блока, BF16, пик **10.22 GiB выделенной PyTorch памяти**.
Это измерение короткого прогона, а не обещание неизменного расхода памяти во всех окружениях.
Полноценное обучение запущено по запросу пользователя; актуальный прогресс находится в `embedding/runs/dinov2_large/train.log`. При сильной сторонней нагрузке на GPU можно
использовать `--batch-size 32 --accumulation 4`; при этом в contrastive loss будет меньше негативов.

## Запуск

В текущем окружении зависимости уже установлены. Проверенные версии: `environment.json` / `requirements.txt`.
Python: `/home/ivan/anaconda3/bin/python`. Если `python` указывает на другую среду, используйте этот полный путь.

```bash
cd /mnt/SSD/workspace/wine
python -m embedding.train \
  --csv data/winesensed_embedding/dataset.csv \
  --output embedding/runs/dinov2_large \
  --epochs 20 --steps-per-epoch 2000 \
  --batch-size 64 --accumulation 2 --precision bf16
```

Одна эпоха здесь — 2000 class-balanced батчей, то есть 128000 выбранных снимков/представлений,
а не гарантированный проход по каждому файлу. `--steps-per-epoch 0` задаёт `ceil(N_train / batch_size)` батчей.
Время зависит от CPU/I/O и параллельной нагрузки на GPU; полное дообучение L-модели рассчитано на длительный запуск.

Результаты в `embedding/runs/dinov2_large/`:

- `best.pt`: компактный checkpoint лучшей модели для инференса, её конфигурация и hash датасета.
- `last.pt`: также оптимизатор, scheduler, scaler и RNG для продолжения обучения.
- `history.csv`: train/val loss, val Recall@1/5, macro Recall, LR, VRAM и время эпох.
- `curves.png`: графики loss, Recall и learning rate; обновляются после каждой эпохи.
- `monitor_queries.csv`, `monitor_gallery.csv`: фактический список val запросов/кандидатов.

Val loss считается на фиксированных P×K батчах из реальных val-пар, без аугментаций и повторения одного файла.
Это вспомогательный показатель; из-за другого семплирования его абсолютное значение не обязано совпадать с train loss.
Модель выбирается по Recall, а не по val loss.

Возобновление с конца последней завершённой эпохи (параметры обучения должны совпадать):

```bash
python -m embedding.train --resume embedding/runs/dinov2_large/last.pt
```

Состояния основных RNG сохраняются. Последовательность аугментаций в persistent worker-процессах
после перезапуска не обязана побитово повторяться. Возобновление внутри незавершённой эпохи не реализовано.

Полные итоговые метрики:

```bash
python -m embedding.evaluate \
  --checkpoint embedding/runs/dinov2_large/best.pt \
  --split val --precision bf16

python -m embedding.evaluate \
  --checkpoint embedding/runs/dinov2_large/best.pt \
  --split test --precision bf16 --save-embeddings
```

Для каждого split сохраняются `metrics.json`, `predictions.csv` с top-5 ID/путями/сходством и `recall.png`.
При `--save-embeddings` также сохраняются `.npy` векторы и CSV с тем же порядком строк.
Технические smoke-test метрики на маленькой выборке **не являются качеством обученного бейзлайна**.

## Использование эмбеддера

```python
from embedding.inference import WineEmbedder

embedder = WineEmbedder('/mnt/SSD/workspace/wine/embedding/runs/dinov2_large/best.pt')
vectors = embedder.embed(['/absolute/path/to/bottle_crop.jpg'])  # shape (1, 512), normalized
results = embedder.search(
    ['/absolute/path/to/new_bottle_crop.jpg'],
    '/mnt/SSD/workspace/wine/embedding/runs/dinov2_large/test/gallery_embeddings.npy',
    '/mnt/SSD/workspace/wine/embedding/runs/dinov2_large/test/gallery.csv', k=5)
```

На вход API подаются уже вырезанные бутылки. `search` предназначен для **новых внешних** запросов:
если подать изображение, уже находящееся в базе, API вернёт и его самого.
Для корректной all-vs-all оценки используйте `embedding.evaluate`, где self-match исключается явно.
Несколько результатов поиска могут относиться к одному вину — галерея содержит все его снимки.

```bash
python -m unittest embedding.test_pipeline -v

```

Проверяются пропорции **классов**, отсутствие пересечений, singleton-политика,
семплирование реальных пар, численная устойчивость loss, совпадение блочного поиска с brute force,
маскирование самого запроса и корректность знаменателя Recall.

Следующие полезные шаги: аудит ложных/пропущенных детекций и дообучение детектора на WineSensed;
поиск близких дубликатов; проверка качества исходных vintage-ID; hard-negative mining;
больше негативов в contrastive батче; сравнение с DINOv3 и отдельной веткой этикетки/OCR.
Это не включено в текущий бейзлайн.
