# Архитектура сканера

Пилот [публичных независимых фотографий](evaluation/PUBLIC_PHOTO_PILOT_2026-09-24.md) по 100 выбранным `slug` дал лишь одну точную пару после ручной проверки источника, винтажа, этикетки и отличия от эталонного снимка. Поэтому он оставлен как диагностический пример: product/source/capture split и обучение на нём были бы фиктивными. Внешняя validation показала, что объединение замороженного и адаптированного Top-20 поднимает candidate recall Norwegian Grocery с 308/317 и 306/317 до 310/317 при списке до 40. На WineSensed объединение детекторного и смешанного (полный кадр + центр) Top-20 дало 848/864 против 844/864 у одного детекторного вида; одиночный смешанный вид дал Top-1 711/864 против 692/864, но Recall@20 843/864. У этих вариантов пока нет проверенного российского полочного набора для выбора реранкера, а цена задержки не измерена для API; рабочий путь не менялся. Официальные фото и собственные магазинные кадры в пилоте не использовались.

Новая [внешняя итерация](evaluation/EXTERNAL_ITERATION_2026-09-24.md) отделена от рабочего API. Она использует те же принципы декодирования и локализации, но обучает residual-голову на 2 284 WineSensed vintages и подтверждённых парах полочный bbox ↔ студийный эталон Norwegian Grocery. Группы одинаковых/близких эталонов и похожих полочных сцен не пересекают split; известные классы из старого эксперимента оставлены только в train. Источник не публикует capture-session ID, поэтому полную независимость сеансов подтвердить нельзя. Реальные query-кропы WineSensed проходят через YOLO и центральный селектор, Norwegian Grocery — через размеченный bbox, что делает его retrieval test оптимистичным по локализации. Каталожные hard-negative пары сохранены для аудита и не используются в loss без подтверждения разных wine identities.

На внешнем test CE-голова улучшила WineSensed Top-1 с 722/908 до 758/908, а на полочных товарах visual reranker изменил Top-1 с 129/206 до 130/206 и снизил Recall@20 с 201/206 до 199/206. OCR ablation дала 131/206, но не превзошла visual-only на validation. Поэтому новый checkpoint в сервис не включён. Все официальные и собственные магазинные фото полностью исключены из этой итерации; скрытый тест организаторов остаётся единственным честным конкурсным измерением.

Экспериментальный путь `YOLO26s → SigLIP2 с обученной residual-головой → реранкер Top‑20` реализован отдельно от сервиса в `evaluation/benchmark_trained_cascade.py`. Он обучен на GRAIN и WineSensed, но на 59 подтверждённых официальных фото дал 39/59 Top‑1 против 51/59 у текущего API и более высокую p95 задержку. Поэтому рабочий путь ниже сохранён. Детектор локализует этикетку, но выбор ближайшей к центру рамки может взять соседнюю бутылку на полке; пример — `IMG_7367.JPG`. Подробный [протокол и хеши](evaluation/TRAINED_CASCADE_2026-09-24.md).

## Путь одного запроса

```text
фото → декодирование и EXIF → 3 кропа: весь кадр, центр, широкий центр
     → SigLIP 2 (768 чисел на кроп) → сравнение с 4 видами каждого из 2 089 эталонов
     → 5 лучших карточек → Qwen3.5-4B: фото + 5 эталонов + текст карточек → P(номер)
     → итог = cosine + 0.02 × log P → точный slug, confidence, top5 → API / карточка / дневник
```

`scanner.catalog` строит детерминированный манифест из `df_2.csv`: дублирующиеся строки одного `slug` схлопываются; расхождения дубликатов отклоняются. Каждый эталон хешируется и индексируется один раз. Если один файл назначен двум карточкам, оба `slug` остаются кандидатами с одинаковой оценкой. Пять карточек без эталона доступны по API карточки, но не участвуют в визуальном поиске.

`scanner.prepare` проверяет исходные архивы по SHA-256 и извлекает из RAR только изображения, указанные в каталоге. `scanner.model_fetch` скачивает закреплённую ревизию SigLIP 2. Манифест, модель, версия предобработки и индекс сверяются при запуске сервиса. Индекс собирается атомарно в `.npz`, рядом хранится метаинформация с хешами.

### Нормализация и визуальный поиск

Для эталона создаются четыре вида: вся бутылка, полоса этикетки (28–84 % высоты), узкая этикетка и корпус без горлышка. Для фото покупателя — весь кадр, центральный кроп и широкий центральный кроп. Каждый вид дополняется белыми полями до квадрата 384×384. Оценка эталона: для каждого кропа фото берётся лучший из четырёх видов эталона, затем три значения усредняются. Такое правило не требует подбирать веса видов и устойчиво к тому, насколько крупно снята этикетка. На 62 размеченных фото оно дало 54/62 Top-1 против 49/62 у прежней схемы `0.35 × кадр + 0.65 × центр`. Поиск перебирает все эталоны; ANN-база для каталога такого размера не нужна.

Проверенные и отклонённые варианты нормализации (на тех же фото): вырезание бутылки COCO-сегментацией YOLO11-seg на белый фон — 49–51/62, модель выбирает соседнюю бутылку или вырезает части этикетки; SigLIP2-so400m вместо base — хуже по Top-1, хотя Top-5 полный; добавление других полевых фото как эталонов — хуже, они совпадают по обстановке, а не по этикетке. Около 12 % эталонов каталога имеют почти идентичного соседа (cosine > 0.97), поэтому глобальный эмбеддинг сам по себе их не различит.

### Проверка кандидатов

Оставшиеся ошибки визуального поиска — карточки одной линии, отличающиеся надписью: сладость, сорт, год. `scanner.verifier` показывает Qwen3.5-4B (ревизия `851bf6e8`, веса проверяются по SHA-256) фото (до 1024 px), пять эталонов (миниатюры 512 px из `data/index/verifier_thumbnails`) и для каждого строку карточки: название, винодельня, цвет, сорт и сладость. Сладость редко выделена в каталоге, поэтому берётся из названия, slug, имени файла эталона или описания. Модель получает принудительный префикс ответа «Кандидат » и отдаёт распределение по цифрам 1–5 за один прямой проход, без генерации текста. Итоговая оценка — `cosine + 0.02 × log P`. Вес выбран на официальных фото (плато 0.015–0.03), поэтому прирост 54 → 59 из 62 — оценка разработки. На GPU модель загружается в 4 битах (около 3,3 GiB), на CPU — в float32.

### Ответ и уверенность

`confidence` — softmax итоговых оценок пяти кандидатов с температурой 0.02: доля первой карточки среди показанных, а не вероятность того, что вино есть в каталоге. `verdict` становится `check_alternatives` при `confidence < 0.7`; это подсказка интерфейсу, организаторский `/v1/eval/predict` всегда возвращает `slug`. Прежний EasyOCR-реранкер сохранён и включается `WINE_OCR=1` при `WINE_VERIFIER=0`.

API загружает по одному экземпляру моделей и индекса при старте и прогоняет один эталон, чтобы первый запрос не был медленным. GPU-инференс сериализован блокировкой. Объём загрузки ограничен 16 MiB. Веб-страница хранит заметки только в `localStorage` браузера.

## Каталожные исправления и подсказки к блюдам

`scanner.reference_fixes` читает отдельный список трёх вручную проверенных замен, сверяет SHA исходного манифеста и файлов, извлекает два отсутствовавших изображения из исходного RAR и пишет `data/catalog_manifest_corrected.json`. Для него индекс строится отдельной командой; исходные манифест и индекс не перезаписываются. Количество эталонов в исправленном индексе — 2 089. Никаких официальных или собственных полочных кадров для выбора этих замен не использовалось.

После распознавания веб-страница запрашивает `GET /v1/wines/{slug}/pairings`. Модуль `scanner.pairing` выбирает три блюда по типу вина и известным признакам; при выборе блюда возвращает пояснение и осторожную оценку сочетания. Правило работает без сети и не меняет визуальное ранжирование, поэтому его результат не следует считать индивидуальной гастрономической экспертизой.

## Что подтверждено

- 27 сентября: на 62 подтверждённых официальных фото (`evaluation/official_labels_v2.tsv`) Top-1 59/62, Top-5 61/62, p50 964 мс, p95 1 146 мс на RTX 3080 с Qwen3.5-4B; без проверки 54/62, p50 388 мс. На CPU Ryzen 5 5600 визуальный поиск занимает p50 1,2 с, проверка Qwen в float32 — около 52 с на фото, поэтому без GPU она по умолчанию выключена. Скрипт организатора прошёл на трёх контрольных фото.
- Все 2 087 эталонов декодируются; перестроенный из RAR набор из 2 087 файлов побайтно совпал с манифестом.
- Текущий индекс создан на RTX 3080 за 169 секунд с batch size 16. Для 100 официальных фото визуальный baseline показал p50 399 мс, p95 437 мс; вариант с OCR — p50 694 мс, p95 1 096 мс. OCR запускался на 51/100 снимках; обе версии укладываются в 10-секундный таймаут открытого скрипта.
- На 17 фото для первичной отладки визуальный Top-1 точен у 14, гибридный — у 16; Top-5 обеих версий содержит ответ у 16. На семи подтверждённых фото других дней обе версии дали 7/7. Остальные из 23 отложенных фото: 11 без точной карточки, пять неоднозначных. Наборы малые и **не представляют случайную тестовую выборку**.
- Скрипт организатора прошёл сквозной HTTP-тест на трёх изображениях. Эталонные ответы к нему не опубликованы, поэтому факт выполнения скрипта не является оценкой качества.

## Ограничения и экспериментальный план

1. **Похожие этикетки.** Проверка Qwen3.5-4B различает сладость, сорт и серию, если правильная карточка попала в пять кандидатов (61 из 62). Вес объединения выбран на тех же фото; нужна независимая съёмка пар-двойников по отдельным сеансам, чтобы подтвердить прирост.
2. **Нет бутылки в каталоге.** По словам организаторов, в закрытом тесте у каждого фото есть slug каталога, а отсутствие ответа считается ошибкой. Поэтому `/v1/eval/predict` всегда отвечает. `verdict` в продуктовом API лишь предлагает интерфейсу показать альтернативы; порог 0.7 не отделяет вина вне каталога (19 из 35 получают ≥0.7).
3. **Несколько бутылок в кадре.** Сейчас выбирается центральная зона, без детектора. Для полочного кадра с несколькими товарами требуется явный выбор пользователя или надёжный детектор/кроп. Пока нельзя считать произвольно выбранную бутылку правильной.
4. **Общие эталоны.** В исходном манифесте у 11 файлов по два `slug`; отдельный [исправленный манифест](evaluation/CATALOG_REFERENCE_AUDIT_2026-09-24.md) сокращает их до девяти после трёх проверенных замен. Остальные случаи не исправлены без точного изображения; визуальные признаки не различат карточки с общим эталоном.
5. **Валидация.** У 100 фото нет официальных ответов. Ручные метки хранят доказательство и SHA каждого файла; данные для настройки модели и финальной проверки нужно разделить до подбора весов или порога.

Прежний код в `embedding/` и `detection/` сохранён как исследовательская основа. Его обученные веса не входили в репозиторий, а прежние метрики на WineSensed не переносятся на конкурсные фотографии.
