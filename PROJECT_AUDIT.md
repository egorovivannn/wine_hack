# Аудит проекта «Сканер российских вин»

Срез на 23 сентября 2026 года. Рабочая ветка: `wine-scanner-development`, исходная ревизия `main`: `21f8992`. Это аудит состояния, а не оценка качества распознавания на скрытом наборе.

## Краткий вывод

В репозитории есть исследовательская основа: код детектора бутылок/этикеток, подготовка кропов, обучение DINOv2-эмбеддера, точный поиск по векторам и восемь проходящих модульных тестов. Рабочего сканера пока нет: отсутствуют обученные веса, HTTP API, мобильный интерфейс и подтверждённая оценка на размеченных фотографиях конкурса. До стоп-кода 29 сентября важнее получить воспроизводимый сквозной baseline и честную локальную валидацию, чем сразу дообучать большую модель.

## Каталог и связи с эталонами

- `df_2.csv`: 4 147 строк, **2 103 уникальных `slug`**. 2 044 повторные строки не должны удваивать вес класса при индексации.
- Для **2 098 карточек** `fname` из `df_2.csv` точно найден в Strapi RAR. Для **5** карточек изображения не найдены; в `df_2.csv` они помечены `is_valid_img=False`.
- У 2 098 карточек **2 087 уникальных файлов**. **11 файлов назначены двум разным `slug`**. Примеры: `aligote-barrel-2024`/`aligote-barrel-2025`, `cabernet-franc-pinot-noir-2021`/`cabernet-franc-pinot-noir-2022`; есть и очевидные конфликтующие пары разных названий. Нельзя выдавать уверенность в точном `slug` там, где эталон буквально один и тот же.
- Сопоставление `df_2.csv` существенно лучше первоначального CSV. Механизм его создания и ручные исключения ещё не документированы; нужен воспроизводимый манифест `slug -> точный файл -> источник решения`.
- В исходном CSV есть ошибки полей категории/сорта. Использовать их для мягкого ранжирования и ручной проверки, а не для жёсткого исключения кандидатов.
- Эталоны отличаются размером и типом: 1 931 RGBA и 156 RGB; ширина от 116 до 6 337 пикселей. Прозрачность, нормализация и сохранение мелкого текста влияют на поиск.

## Что реально работает в коде

| Часть | Состояние | Ограничение |
| --- | --- | --- |
| `embedding/core.py`, `embedding/inference.py` | Реализованы подготовка кадра, DINOv2-модель, эмбеддинги и точный top-k поиск | Нет весов в клоне; обучение и проверка описаны для другого датасета |
| `embedding/test_pipeline.py` | **8 из 8 тестов прошли** на домашней машине | Проверяют вычислительные компоненты, а не качество на конкурсных фото |
| `detection/training/` | Есть сценарии обучения и предсказания YOLO | Веса и обучающие файлы отсутствуют; `ultralytics` и `cv2` в системном Python сейчас не установлены |
| `df_2.csv` | Почти полный точный указатель на файлы RAR | Дубли строк, 5 отсутствующих эталонов, 11 коллизий файлов |
| `bottle_embeddings.py`, `embedding/competition_labels.py` | Намечена связка детекция → векторы → поиск | Жёсткие пути к отсутствующим `best.pt`; готовой базы эмбеддингов нет |
| HTTP API / мобильный UI | Не найдены | Скрипт организатора пока не к чему подключить |
| `README.md` | Только заголовок | Нет запуска с чистой машины, конфигурации, ограничений |

В сохранённых `embedding/qa/verification.json` и `embedding/smoke_class_disjoint/` есть технические результаты с другого хоста и WineSensed. Они **не являются конкурсной точностью**. В документации указан пик 10.22 GiB выделенной памяти при BF16 и batch 64 на RTX 3090 Ti; такая конфигурация не помещается в доступные 10 GiB RTX 3080 без изменения режима обучения.

## Главные риски для оценки

1. **Нет проверенных меток полевых фото.** Ни старые три, ни новые 100 официальных снимков не содержат опубликованной таблицы правильных `slug`. У собственных 13 снимков тоже нет готовой разметки. Пока нельзя оценить Accuracy@1/F1.
2. **Неоднозначные карточки.** Один эталонный файл у двух `slug` и несколько бутылок в кадре требуют решения по конкретному товару и правилу выбора целевой бутылки.
3. **Нет запуска сквозного сценария.** Обучающий код и тесты не заменяют сервис `POST image -> {"slug":"..."}` и карточку.
4. **Разница оборудования.** Текущие примеры обучения и память измерены на 24 GiB видеокарте; на 10 GiB параметры нужно менять и измерять заново.
5. **Срок.** По заметкам организаторов, стоп-код — 29 сентября 2026 года, 23:59 МСК. Сданную версию после него менять нельзя; ссылки и доступность нужно проверить заранее.

## Предлагаемый порядок до стоп-кода

1. **Разметка и правила (первый приоритет):** записать ожидаемый `slug` для полевых фото с доказательством по видимой этикетке; явно отметить `unknown` и `ambiguous`; часть съёмок удержать для финальной проверки. Письменно уточнить у организатора неизвестные вина, несколько бутылок и эквивалентные карточки.
2. **Запускаемый baseline:** выбрать доступные веса, подготовить эталонные эмбеддинги по 2 087 изображениям, обработать ориентацию и кроп целевой бутылки, сделать top-1/top-5 поиск по уникальным `slug`. Сначала измерить качество и ошибки без дообучения.
3. **Исправить крупные ошибки:** проверить альтернативный визуальный энкодер и OCR названия/года/категории для похожих серий; сохранять отдельную оценку на таких случаях. Не опираться на неверные поля CSV как на жёсткие фильтры.
4. **Сервис и продукт:** реализовать контракт скрипта организатора, мобильную карточку и одну законченную функцию после поиска. Измерить задержку end-to-end, включая декодирование и детекцию.
5. **Сдача:** обновить README и ARCHITECTURE, зафиксировать окружение и веса, подготовить демо и презентацию по обязательному шаблону, заморозить проверенный коммит до стоп-кода.

Критерий для решения о дообучении: оно должно улучшить удержанную реальную выборку по сравнению с воспроизводимым baseline. Технический smoke-test или хорошая метрика WineSensed этого не доказывают.
